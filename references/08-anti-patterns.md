# 08 · 反模式：看起来对、实际会出事

> 每一条都是**真实踩过**或**在语料里被验证过**的。格式：错误做法 → 为什么错 → 应该怎么做。

---

## A. 调试姿势

### A1. 用"启动方案 + 等 cron"来调试
**为什么错**：测试环境没有守护进程，启动了也不产生队列；有守护进程时又要等一个调度周期，
而且失败会被退避重试藏起来（最长约 25 小时）。
**应该**：`dispatchSource` → `queue.job.run`，同步拿结果（见 `03-debug-loop.md`）。

### A2. 一看到报错就改元数据
**为什么错**：元数据改动影响后续所有调度，且很难判断"是这次改对了还是上次碰巧"。
**应该**：先改**任务参数**（`queue.job.update`）验证假设，调通后再回写元数据。

### A3. 把 `ok=true` 当成"数据取到了/写进去了"
**为什么错**：平台把"源系统返回空"当完成；目标 `status=FINISHED` 也只代表报文成功。
**应该**：看 `has_data`；目标侧**回查外部系统**。

### A4. 看到 `dbInfo` 有 fatal 就去找异常
**为什么错**：老版本把调试留痕写成 FATAL，`exception.search` 永远是 0。
**应该**：先看日志文本是否 `0x_debug_` 开头；新版看 `log.debug` 计数。

## B. 配置姿势

### B1. 目标端字段直接写字段名（裸名）
```jsonc
{"field":"FBillNo","value":"FBillNo"}     // ❌ 常量
{"field":"FBillNo","value":"{{FBillNo}}"} // ✅ 取值
```
**为什么错**：裸名不查数据，原样当常量；撞上 `CURRENT_TIME` 之类还会被替换。
这是"字段都填了但写出去是空 Model"的头号原因。

### B2. 基础资料字段不加 parser
**为什么错**：金蝶要 `{FNumber:"…"}` 而不是 `"…"`，直接报"格式错误，不能转换为字典类型"。
**应该**：`ConvertObjectParser` + `params=FNumber`。

### B3. 明细逐行映射，不用别名
**为什么错**：金蝶主子表用 `"FSaleOrderEntry": "_Flist"` 把明细数组挂上去；逐行映射会变成多张单。
**应该**：先确认"一单一条"还是"一单多行"（`id` 取 `FBillNo` 还是行 ID）。

### B4. 靠 `meta_data.type` 判断读写方向
**为什么错**：`type` 有双重历史语义（旧资产=方向，新资产=协议），判断必然出错。
**应该**：方向看它挂在 `source` 还是 `target`；协议看资产 `type`；读写看资产 `effect`。

### B5. 随手改 `idCheck`
**为什么错**：它是 ADATA 落库去重开关，与目标写入无关；改成 `false` 会改变落地语义。
**应该**：保持默认 `true`；幂等靠**业务唯一键**。

### B6. 用 `_function` 写复杂表达式
**为什么错**：它把后半段当 MySQL 执行（注入面）；**失败时不报错**，会把半截 SQL 写进业务字段。
**应该**：能落地成字段就落地；必须用则单独验证返回值。

## C. 运维姿势

### C1. 拿 `queue.list` 看参数
**为什么错**：列表接口把 `params` 抹掉了，你看到的是空。
**应该**：`queue.job.get`。

### C2. 把 `jobId` 和业务编号混用
**为什么错**：`jobId` 是 24 位十六进制，业务编号是 `number`；传错报 `invalid_job_id`。
**应该**：`queue.list` 拿 `jobId`；`data.search {number:…}` 查业务编号。

### C3. 用裸数字改数据状态
**为什么错**：`0`/`2` 的语义与直觉相反（`0`=waiting、`2`=finished），传错会静默丢数据。
**应该**：只用语义词 `await/error/queue/finished/repeat/unhandle/continue/fkc`。

### C4. 在共用的开发库跑会重建表的测试
**为什么错**：`dh_mcp_grant` 被 drop 重建 → **所有 MCP 密钥失效**（真实发生过）。
**应该**：测试用独立库；或用带安全阀的测试（`MCP_TEST_ALLOW_SCHEMA_RESET=1` 才执行）。

### C5. 靠"再推一次"实现删除/作废
**为什么错**：集成只负责写，不负责撤；目标是 insert/upsert，不会删旧单。
**应该**：单独设计反向链路（作废/红冲/禁用），并与正向链路使用不同幂等键。

### C6. 在 `AfterTargetInvoke` 里抛异常"撤销"
**为什么错**：目标端事件异常被**静默吞掉**，目标已落库，抛异常只可能触发重试。
**应该**：写入前校验；失败用反向链路补偿。

### C7. 用事件脚本手写 `if/else` 做值翻译
**为什么错**：`1/2/0 → 男/女/未知` 这类对照表写进脚本后，业务改一次就要改脚本、发布、重新联调；
且脚本异常在目标端会被吞掉，出问题极难定位。
**应该**：用静态映射（`mapping.*`），业务改值只改表不碰代码；脚本只留给真正的逻辑判断。
两者分工：**静态对照用映射，规则计算用 parser/脚本**。

### C8. 把映射挂在源端顶层字段上，然后怀疑平台
**为什么错**：`QueryCollation::run()` 对顶层标量**根本不调用** `_mapping`，只有 object/array 子项会翻译（`01` §3.7）。
**应该**：映射挂目标端字段（`ExecuteCollation` 顶层也生效）；源端只能挂嵌套子字段。

## D. 安全姿势

### D1. 用 REST 拉连接器配置并落盘
**为什么错**：REST **明文返回 `app_secret`**，一旦进日志/仓库就是泄露。
**应该**：用 MCP（已脱敏）；需要轮换凭据去平台页面操作。

### D2. 把 `qk_live_…` / `sh-…` 写进示例或 issue
**为什么错**：密钥即权限；`plaintext` 只出现一次，泄露无法"找回"只能轮换。
**应该**：环境变量 / 密钥管理；示例里写 `<YOUR_KEY>`。

### D3. 为了"一次成功"跳过 `precheck`
**为什么错**：影响面 1500 行和 10 行不是同一量级；跳过预演等于放弃唯一的复核机会。
**应该**：先 `dryRun` 或看默认返回的 `precheck`，再决定是否带令牌。

### D4. 直接改客户生产方案
**为什么错**：没有回滚点、影响面不可控、审计上说不清。
**应该**：`strategy.copy` 副本上改；确需改生产先备份（`source.update`/`target.update` 自动备份）。

## E. 表达姿势（对人类的输出）

### E1. 只报"成功/失败"
**为什么错**：人类无法复核，也无法判断是否要回滚。
**应该**：结论 + 证据（id/关键字段/错误码）+ 动作（哪些有副作用）+ 下一步。

### E2. 报"已写入"但没回查
**为什么错**：平台状态不是业务事实。
**应该**：写明"平台返回成功，未回查"或给出回查结果。

### E3. 搬运整段配置/日志
**为什么错**：几十 KB 的 `meta_data` 会淹没结论，且可能含敏感字段。
**应该**：只给差异字段与关键数字；完整内容给"怎么取"的命令。
